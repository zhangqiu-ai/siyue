# Siyue prototype → React Native (Expo) rebuild spec

## Space (goals) screens + Plan-creation screens

Sources (read-only; no repo file was modified):

- `docs/design/prototype/siyue-prototype.html` (1262 lines). CSS lines 7–391; theme tokens lines 11–12; component CSS 42–389; the screens in scope at 880–966, sheets 1017–1028, device/shell 1088–1156.
- `docs/design/ui-acceptance.md` (153 lines).

Everything below is copied from those two files. Values are exact; none has been rounded or inferred except where explicitly labelled **inference**. `apps/mobile/src/ui/theme.ts` was **not** read (out of the stated scope), so the theme mapping in §1 is derived from the comment at prototype line 10 only.

Conventions used in this document:

- `L('zh','en')` → the prototype prints zh when lang=zh, en when lang=en. Both strings are given everywhere.
- `weight 650` is a real CSS value in the prototype (`h1.lt`, `.result h1`, `.titleinput`, `.sheet h2`, `.spbadge`, `.tile .av`). In RN map 650 → `'600'` unless the project already has a 650 token; RN accepts numeric 650 on iOS but Android snaps to the nearest available weight.
- Every divider is a 1px pseudo-element with `transform:scaleY(.5)` → **0.5 px hairline**. In RN use `height: StyleSheet.hairlineWidth` or `0.5`.
- `place-items:center` on a grid = centred child → RN `alignItems:'center', justifyContent:'center'`.
- All `display:grid` usages inside these screens are single-item centring; there is no real grid layout to port.

### Visual and interaction checks that apply

UI-V01 焦点 (one primary task per screen; the draft page keeps one primary plus one text secondary); UI-V02 文案 (the brand appears only at the top of the mobile sidebar — `space.home` must not repeat it); UI-V03 对齐 (left/right edges and text baselines aligned; the trailing arrow and status share one alignment line — `.chev`, `.gmeta`, `.due`); UI-V04 节奏 (same-semantics spacing and radii consistent, tighter inside a group than between groups); UI-V05 字体 (system font; zh/en/digit mixing without clipping; do not disable system text scaling to make screenshots look good); UI-V07 色彩 (only light and dark; semantic colour pairs checked in both themes; never convey state by colour alone — `due.today`, `.warn` and the done state all need a text or icon cue); UI-V08 对比度 (**≥4.5:1** for body, labels and meaningful hint text; **≥3:1** for non-text graphics needed to identify a control or state; disabled controls are exempt but must be explainable); UI-V09 内容压力 (empty / 1 item / 20 items, 2× title length, zh-en mixing, no overlap; only list summaries may truncate); UI-I01 可操作 (icon-only controls need an accurate name, role and selected/expanded state — the FAB, avatar stack, nav buttons and task checkboxes all carry aria-labels in the prototype); UI-I03 输入 (the draft page and the add-task row stay reachable with the keyboard open; the bottom safe area is not covered); UI-I04 编辑保护 (the autosave-plus-discard-confirmation policy is specified; do not add a confirm dialog on untouched returns); UI-I05 加载 (immediate press/busy feedback, no duplicate submit, no layout jump — the confirm button's 900 ms busy spinner); UI-I07 空/离线 (empty is not a load failure; offline keeps content; the empty-space and offline-sync states here); UI-I10 无障碍 (VoiceOver/TalkBack reading order, decorative elements not read twice, status not over-announced; desktop Tab traversal, visible focus, Escape); UI-I11 动效 (150–250 ms start point for custom micro-feedback; respect reduce-motion).

### Device, language, font-scale, dark-mode and iPad rules (§5 matrix)

- 中文与英文均为必需. M/L changes touching copy or layout require both languages on the affected pages and applicable states, cross-covered with the iPhone/iPad matrix for key input, navigation, sheet and error paths. Record the actual locale; missing language coverage must be marked `not_run`.
- Also check resource-key completeness and that no raw keys, missing translations or unexpected language mixing appear; accessibility names validated in both languages.
- M/L mobile pages: **iPhone and iPad must both be checked**, light and dark covering the affected components. iPhone covers a compact width (**around logical 375**) and a wider phone (**around 430**); iPad covers landscape, portrait and the currently supported narrow-window/split widths with real size switching. Record device, OS and actual available logical size — the numbers are not device models and breakpoints must not be assumed identical.
- iPad content width, navigation, sheets and input areas are organised around available space, not a stretched phone layout; whether to use a split view and the exact breakpoint is confirmed per prototype/spec. Rotating, resizing or toggling the keyboard must not lose input, duplicate submits or make the primary action unreachable.
- iPad text input must be checked with both the on-screen and an external keyboard (edit/send/focus paths); with no device available mark `not_run` — an iPhone or simulator result cannot stand in for iPad acceptance.
- Text/form-related: default font size plus **one larger accessibility size (e.g. AX3, record the actual step)**; Web text zoom **200%**. On narrow screens with large text, wrapping, growth and scrolling are allowed; a required action must never become unreachable.
- Keyboard-related: keyboard open/closed, multiline and long input — both screenshot and interaction, not only the keyboard-closed first screen.
- Shared components or layout changes: Android needs applicable native checks; if the environment is not ready write `not_run` — iOS passing does not sign off Android.
- Screenshots use synthetic data (no API keys, no private sessions), same device/theme/font size/data for before-after; different conditions must be noted and are reference only, not pixel comparisons.
- Native permissions, touch feel and performance-sensitive changes still need a real device; simulators are iteration only and do not replace release acceptance.
